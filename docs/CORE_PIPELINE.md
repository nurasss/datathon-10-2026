пакетов больше не используется. Для работы указанным интерпретатором:


Экспорты ONNX включены в ветку; повторная конвертация при запуске не нужна.

Рабочий путь — `vision.pipeline.VideoAnalyzer`. Старые `events.detect_ev01` /
`detect_ev02` оставлены для исторических dev-скриптов, но **не вызываются** им;
даже их конфигурация по умолчанию выключена. Сам уход не является нарушением.

## Проходы, память, CPU

- NanoDet: только `CPUExecutionProvider`, последовательный ORT, выключенное
  spinning; число intra-op потоков задаёт `detector.intra_op_num_threads`.
- Редкая сетка задаётся `sampling.coarse_fps`; кандидатные окна определяются
  изменениями числа / положения людей относительно рабочего места и движением.
  Детектор плотного прохода запускается только внутри объединённых окон.
- Исходное видео декодируется один раз на плотной временной сетке. Вне окон
  эти кадры **не проходят** инференс: хранится только ограниченный JPEG-кэш.
  При переполнении кэш освобождается и окна декодируются повторно. Предел
  задаёт `sampling.cache_max_mb`; это не кэш всех исходных видеокадров.
- Постоянное состояние сцены проверяется также в начальном окне. Незаметное
  движение рук вне окон может остаться без плотного прохода — это ограничение,
  а не отрицательное визуальное заключение.
- Разрешения можно разнести: `coarse_input_size` / `coarse_model_path` и
  `input_size` / `model_path`. Профилировщик с `--size` проверяет одинаковое
  разрешение в обоих проходах, без флага — текущую рабочую конфигурацию.
  По сохранённому сравнению выбрано одинаковое разрешение обоих проходов;
  меньший экспорт оставлен для экспериментов, не для потери найденных людей.

## Треки, роли, действия

`tracking.py` — собственный IoU/Kalman-трекер под MIT; high-score ассоциация,
low-score recovery без рождения новых low-score треков, возраст в секундах.
Для трекинга исключаются вложенные/перекрывающиеся дубликаты; сырые COCO-боксы
при этом остаются в trace.

Кассир определяется по времени занятия рабочего места, а не числу кадров;
сама зона выбирается на равномерном обзоре. Вошедший —
появление трека через область двери. Остальные — `client_other`. Эти роли не
доказывают личность, должность или полномочия. Геометрия двери задаётся через
`zones.door_rect`: это некалиброванный prior, а не визуальная детекция двери.
Для другого ракурса необходима проверка зон и ролей.

`triggers.py` отделён от `rule_engine.py`: начало вставания / входа сохраняется
как действие, но без положительного состояния сцены обычный уход не выдаётся
как нарушение. Счётчик людей использует подтверждённые треки в рабочей части
кадра, исключая очень маленькие частичные фигуры; его prior пишется в trace.

## Контракт сцены

`scene_state.py` интегрирован из ветки сцены; ядро не переписывает его классификаторы.
На кадрах плотного прохода вызывается `analyze_scene` пакетами. Каждая
детекция: `cls`, `score`, нормированный `box` в формате xyxy; передаются **все**
COCO-классы выше порога. В trace есть отдельные `detections`, `persons` с ID и
ролью, `desk_objects` и сериализованный `scene`. Laptop не входит в
`desk_objects` и не является основанием для правила личных вещей.

Семантический контракт сцены: `cash`, `cash_bag`, `cup`, `phone`, `food`,
`clothing_or_bag`, `other`. Ценности — **только** `cash` / `cash_bag`.
`clothing_or_bag`, `handbag`, `backpack` относятся к личным вещам, не к ценностям.
`document`
означает рабочий документ на экране, а не просто свечение монитора. Неизвестное
состояние — `None`, оно не подтверждает нарушения и прерывает удержание двери.

Наличие COCO cup/phone в сыром trace само по себе **не** включает сценозависимые
правила. Неизвестное состояние сцены не заменяется ни положительным, ни
отрицательным заключением. Контекст сцены сохраняет опорный кадр на весь ролик,
найденную локализацию двери/сейфа и стационарного оборудования. Стол не
подменяется зоной человека: при найденном ноутбуке поверхность привязывается к
оборудованию, иначе остаётся автоматическая локализация модуля сцены. Эта
локализация, как и геометрический prior двери, не гарантирует правильную область.

## Устойчивость и конфигурация

`rules.types.<CODE>` содержит `enabled`, `threshold`, `min_frames`, `min_sec`,
`max_gap_sec`, `lookback_sec`; для подтверждения закрытия — `clear_frames` и
`clear_sec`. Все они попадают в эффективный config манифеста evaluate.
PERSONAL_ITEMS и MANUAL_COUNT по умолчанию требуют повышенного порога и
устойчивости на плотных кадрах. Время между редкими кадрами не считается
непрерывным наблюдением. Короткие всплески/неизвестные кадры не подтверждают правило.

`triggers` настраивает подтверждение отсутствия/возврата, привязку к рабочему
месту, соединение фрагментов и условия входа. Триггеры формируются без labels.
Фрагменты кассира объединяются в логическую идентичность с сохранением исходных
ID в `cashier_track_aliases`, а независимые одновременно видимые люди не должны
объединяться. У входа различаются новый человек и изменившийся бокс уходящего
клиента; неподвижный бокс на оборудовании не считается проходом через дверь.

`results.csv.type_ok` — точное равенство наборов предсказанных и размеченных кодов;
`type_hit` — наличие хотя бы одного общего кода. Доля правильных типов среди TP
не равна video-level precision. `triggers.json` считает попадания относительно
`events.csv.start_sec`; строки NONE не дают времени действия и оцениваются
отдельно по наличию триггера и отсутствию нарушения.

## Нормы и evidence

Реестр перенесён только из файла куратора; цитаты и оговорки не переписаны.
Названия типов и связь с rule_id — `rules.registry.TAXONOMY`. Нормативная
гипотеза содержит номер акта, пункт, дословную цитату, URL и `cannot_infer`.
Для OUTSIDER описывается риск нарушения режима изоляции, не утверждается
незаконность присутствия. Для экрана не приписывается несуществующая обязанность
ручной блокировки: используется оговорка об автоблокировке по неактивности.

Таймкод — начало действия/первое наблюдение состояния, не середина эпизода.
Evidence: до начала, начало, после начала. Если начало уже вне доступной
записи, предшествующий кадр нельзя восстановить: время ограничивается записью.

## Проверки без повторного полного инференса

`scripts/evaluate.py --oracle-events <events.csv>` выполняет один проход зрения
и затем два дешёвых replay того же движка:

- `oracle/scene_only_results.csv`: идеальные сцены, наблюдённые триггеры/роли;
- `oracle/results.csv`: идеальные сцены **и действия**, верхняя граница движка.

Второй результат нельзя называть точностью зрения. Поддерживаются утверждённые
коды и явные соответствия старых кодов CSV. Для неподдержанного типа норма
не изобретается; такая строка сохраняется в `oracle/metrics.json`.

`scripts/core_load_run.py` запускает собственный сервер только на loopback
тестового порта, выполняет один пакет одновременных загрузок, сохраняет сырые
HTTP-опросы, записи БД, отчёты worker и останавливает только свой процесс.
Чужой основной сервер не вызывается и не останавливается.

## Протокол задачи 4

Целевые evaluate запускаются через `--only`; их каталоги не перезаписываются.
`scripts/replay_actions.py --source <trace-dir> --only <IDs> --out <new-dir>`
использует сохранённые детекции и состояния, без повторного нейроинференса.
Ранние trace без `tracking_detections` не содержат всех low-score боксов;
replay явно отмечает неполноту и не считается end-to-end оценкой.

Единственный финальный полный запуск обёрнут в `scripts/run_task4_final.py`.
Он эксклюзивно создаёт `artifacts/task4/full_run.json` и отказывает при повторе;
даже ошибка не даёт автоматического разрешения повторить запуск.
`scripts/report_task4.py --eval-dir artifacts/task4/final` и
`scripts/audit_task4.py --eval-dir artifacts/task4/final` только обрабатывают
сохранённые файлы, без инференса. Исторический нагрузочный тест не повторяется.
