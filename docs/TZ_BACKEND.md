# ТЗ Backend, CV/ML и инфраструктура — ForteVision

Версия: 1.0 · Дата: 17.10.2026

Связанный документ: [ТЗ Frontend](./TZ_FRONTEND.md).

## 1. Основание и приоритет требований

Источники: `Кейс_ForteBank.docx`, `ForteBank_MASTER_TZ_v2.0_Единое.docx`, локальный датасет и исходный код `forte-vision`.

- **[К]** — обязательное требование исходного кейса.
- **[П]** — проектное решение, обязательное по этому ТЗ, но не отдельное требование организатора.
- **[У]** — требует подтверждения; не считать доказанным.

Первичен исходный кейс. Документ задаёт целевое состояние; наличие функции в коде ещё не означает её приёмку.

## 2. Цель и ответственность

**[К]** Принимать новые MOV, асинхронно анализировать визуальные действия локальными моделями и возвращать вердикт, события, таймкоды, реальные кадры и нормативные объяснения не позднее 300 секунд.

Backend отвечает за:

- публичный API жюри и браузерный API;
- аутентификацию, валидацию, очереди, жизненный цикл и хранение;
- декодирование, локальный CV/ML, временную логику, классификацию;
- работу с разметкой, измерение качества, выбор порогов;
- доказательные JPEG и нормативный mapper;
- безопасную выдачу видео для UI;
- развёртывание, ограничения ресурсов, очистку, наблюдаемость и тесты.

Не входят: АБИС, внутренние банковские журналы, транзакционный antifraud, лица, звук, live CCTV, автоматические дисциплинарные решения, точное определение суммы наличных.

## 3. Безусловные ограничения [К]

1. Не передавать видео, кадры или их описания облачным LLM/VLM, OCR/vision и другим AI API.
2. Все модели исполняются внутри собственного развёрнутого сервиса; после подготовки весов инференс работает без интернета.
3. Не использовать звук, распознавание и идентификацию лиц.
4. Не обучать и не калибровать модель на тестовых материалах жюри; не публиковать и не передавать их третьим лицам.
5. Не делать выводы о невидимых фактах: проводках, полномочиях, документальной сверке, составе неразличимого предмета.
6. Использовать допустимые компоненты с подтверждёнными лицензиями на коммерческое использование. Лицензии кода и весов проверяются отдельно.

Собственный VPS/GPU-сервер допустим: локальность означает выполнение моделей внутри командного сервиса, а не обязательную работу на пользовательском ноутбуке.

## 4. Исходные данные и обязательная подготовка

Проверенный путь: `../data_raw/open/` относительно корня `forte-vision`.

| Параметр | Проверенный факт |
|---|---|
| Видео | 42 MOV, 40 уникальных по SHA-256 |
| Разметка | 22 положительных, 20 отрицательных строк |
| Уникальные видео по классам | 21 положительное, 19 отрицательных |
| Видео/звук | H.264, 464×848, без аудио |
| Средний FPS файлов | примерно 29,758–30 |
| Длительность | 11,63–142,53 с |
| Объём одного видео | 2,43–28,72 МБ |
| Дубликаты | Х-4 = Х-47; Х-5 = Х-48 |
| Особый случай | Х-4: 57 с; Х-47: 68 с при одинаковом видео |

**[П]** Подготовить manifest с нормализованным clip_id, SHA-256, длительностью, параметрами, исходной меткой и временем. Нормализовать латинскую `X` и кириллическую `Х`, не переименовывая исходники без необходимости.

**[П]** Полностью просмотреть и аннотировать все уникальные ролики. Наличие метки не устанавливает тип события или юридическую квалификацию.

Минимальная аннотация: `clip_id`, `sha256`, исходная метка/таймкод, `event_id`, `start_sec`, `peak_sec`, `end_sec`, тип-кандидат, описание видимого действия, видимость, `rule_id`, статус проверки, annotator/reviewer и замечания. Для отрицательных видео фиксировать сложные контрпримеры.

Оба времени Х-4/Х-47 сохранить до экспертного решения. Не выбирать одно автоматически.

**[П]** Split проводится по уникальным видео и группам дубликатов, по возможности также сценариям/сценам. Кадры одного видео не распределяются между train и validation. Отдельно проверить другой ракурс; если такого материала нет, явно зафиксировать отсутствие подтверждения устойчивости.

## 5. Публичный API жюри

### 5.1. Авторизация [К/П]

Оба endpoint требуют заголовок `X-API-Key`. Нет/неверный ключ → 401 или 403, задача не создаётся. Ключи хранятся в secret env, сравниваются безопасно, не попадают в URL/логи.

**[П]** При нескольких ключах хранить владельца задачи и проверять доступ к её результату. Непредсказуемый ID не заменяет авторизацию.

### 5.2. POST `/api/v1/analyze`

- **[К]** `multipart/form-data`, поле `file`, `.mov`.
- **[П]** Успех: HTTP 202, минимальный ответ:

```json
{"job_id":"opaque-id"}
```

**[У]** Проверить принятие HTTP 202 интеграционным валидатором организатора, если он доступен.

Приём файла потоковый с лимитом размера. Имя файла не используется как путь. Нулевая длина, неверный контейнер, превышение лимитов и отсутствие видеодорожки отклоняются безопасно.

**[П] Критический инвариант:** worker не видит задачу как готовую к исполнению до полного сохранения, закрытия файла и успешной предварительной проверки. Допустим внутренний статус `uploading`; переход в `queued` выполняется атомарно после готовности файла.

При оборванной загрузке удалять частичный файл и освобождать резерв очереди. Полный анализ не запускается внутри HTTP-запроса.

### 5.3. GET `/api/v1/jobs/{job_id}`

В процессе:

```json
{"job_id":"opaque-id","status":"processing"}
```

Технический сбой:

```json
{"job_id":"opaque-id","status":"failed"}
```

Нет событий:

```json
{"job_id":"opaque-id","status":"done","verdict":"no_violation","violations":[]}
```

При событии `status=done`, `verdict=violation`, массив `violations` содержит один или несколько объектов строго следующих типов:

```typescript
type Violation = {
  type: string;
  timecode_sec: number;
  description: string;
  evidence_frames: {
    timestamp_sec: number;
    image_base64: string;
  }[];
};
```

Это описание контракта, а не требование использовать TypeScript на backend. `image_base64` содержит полный JPEG, не URL и не data URI. Нормативная привязка включается в `description`, отдельная структура хранится внутренне.

**[П]** До подтверждения совместимости не добавлять в API жюри `progress`, `phase`, `normative_source`, `error` и поля со значением null. Расширенные метаданные выдавать браузерным API.

### 5.4. Инварианты результата

- `done` → обязательны `verdict` и `violations`.
- `no_violation` → массив пуст; `violation` → минимум одно событие.
- `type` и `description` содержательны и непусты.
- События отсортированы по времени; повторы одного эпизода удалены.
- На событие приходится 1–3 полностью декодируемых JPEG.
- Время события и кадров находится в пределах длительности исходника.
- Нельзя возвращать `inconclusive` как третий вердикт без изменения контракта организатором.
- Сбой декодирования/модели/извлечения обязательных evidence не маскируется под `no_violation`.
- Терминальный результат публикуется атомарно после проверки событий и кадров.
- Потеря evidence после положительного анализа не должна менять результат на отрицательный: вернуть безопасный сбой/недоступность, а не пересчитать вердикт из оставшихся файлов.

### 5.5. Ошибки [П]

| Код | Сценарий |
|---|---|
| 401/403 | неверная аутентификация/доступ |
| 400/415/422 | неверный запрос, формат, пустое или невалидное видео |
| 413 | превышение размера |
| 404 | неизвестная задача |
| 410 либо документированный 404 | результат удалён по TTL |
| 429/503 | ограничение нагрузки / очередь недоступна |
| 500 | безопасная внутренняя ошибка |

Не возвращать внутренние пути, секреты, stack trace и сырые сообщения decoder/model.

## 6. Браузерный API и медиавыдача [П]

Согласованный с Frontend same-origin контракт:

| Метод | Endpoint | Поведение |
|---|---|---|
| POST | `/ui/api/session` | JSON `{ "api_key": "..." }`, проверка ключа, HTTP 204 + session cookie |
| DELETE | `/ui/api/session` | HTTP 204, завершение сессии |
| GET | `/ui/api/config` | `allowed_extensions`, `max_upload_bytes`, `deadline_sec` |
| POST | `/ui/api/analyze` | multipart `file`, HTTP 202 + `job_id` |
| GET | `/ui/api/jobs/{job_id}` | `{ "job": <публичная схема>, "meta": <UI-метаданные> }` |
| GET | `/ui/api/jobs/{job_id}/video` | защищённый медиапоток с Range/206 |

Все endpoint, кроме создания сессии, требуют действующую сессию. Cookie: `HttpOnly`, `Secure` в HTTPS-развёртывании, `SameSite=Lax`; TTL конфигурируется. Изменяющие запросы защищаются проверкой Origin. Ключ не возвращается клиенту после входа.

`meta` всегда содержит: `filename`, `duration_sec`, `stage`, `progress`, `video_url`, `event_details`, `error_code`, `error_message`. Недоступные скаляры — null; `event_details` — массив.

- `stage`: `queued|probe|decode|reasoning|evidence|finalize|finished`.
- `progress`: 0..1 либо null, только измеренная оценка.
- `event_details[]`: `violation_index`, `observation` (строка/null), `rule_reference` с `title`, `paragraph` (строка/null), `url`.
- Для `failed` предусмотрены безопасные код и пояснение в `meta`.
- `job` не содержит браузерных расширений и совпадает с публичной схемой жюри.

API жюри и браузера используют одну бизнес-логику. Браузерный endpoint не должен повторно ставить задачу в очередь через сетевой вызов публичного API.

Видеопоток не читать целиком в RAM ради одного ответа. Обеспечить seek. При несовместимости MOV с браузером подготовить локальную MP4/H.264-копию без аудио и со сохранённой временной привязкой. Её подготовка не должна блокировать выдачу результата жюри за 300 секунд. Evidence извлекать из исходного видео, а не из демонстрационной копии.

## 7. Жизненный цикл, очередь и SLA

Внутренние состояния: `uploading → queued → processing → done|failed`. Снаружи очередь отображается как `processing`.

- **[К]** Полный результат жюри — не позднее пяти минут; failed не считается успешной обработкой.
- **[П]** Замерять wall-clock от начала загрузки у клиента до получения готового JSON через GET. Сервер ведёт собственный deadline от начала приёма запроса, не от запуска модели.
- **[П]** Внутренний целевой бюджет — до 240 секунд с резервом на передачу/опрос. Это проектная цель, не обещание измеренной скорости.
- **[П]** Timeout worker учитывает остаток общего deadline, включая ожидание очереди.
- **[П]** Ёмкость очереди, параллельность и admission control выбираются по измеренному throughput. «Очередь 6» сама по себе не гарантирует SLA.
- **[П]** Подтвердить одиночный запуск и серию из 5+ конкурентных запросов; при нехватке мощности фиксировать ограничение, а не обещать соблюдение SLA.
- **[П]** Захват задачи worker атомарный. Один job не исполняется двумя worker.
- **[П]** Сбой/перезапуск worker не оставляет вечный processing. Watchdog завершает просроченные jobs и удаляет временные файлы.
- **[П]** Вложения, состояние и результаты разных задач изолированы.

Допустим SQLite + один управляемый worker при доказанной корректности. При нескольких процессах/worker использовать подходящее общее хранилище и очередь. Redis/PostgreSQL/GPU не обязательны сами по себе.

## 8. Локальный CV/ML-конвейер

Целевой pipeline [П]:

1. **Ingest/QA:** ffprobe, контейнер/кодек/разрешение/длительность, лимиты ресурсов, отсутствие декодирования аудио.
2. **Время:** использовать presentation timestamps; время evidence подтверждается фактическим кадром. Средний FPS не считать достаточным доказательством корректности VFR.
3. **Быстрый проход:** локальная детекция людей/предметов и движения, определение зон, трекинг без идентификации личности.
4. **Кандидаты:** изменения зон/состояний и последовательности действий.
5. **Уточнение:** плотнее исследовать окна кандидатов, если это нужно для локализации и устранения ошибок редкой выборки.
6. **Временная логика:** устойчивость, длительность, пред-/постконтекст, независимые события, склейка повторов.
7. **Решение:** калиброванные пороги по проверенным категориям; никакой подмены классификации юридическими догадками.
8. **Evidence:** 1–3 реальных JPEG из исходника, по возможности до/во время/после события.
9. **Legal mapper:** только утверждённый реестр; никаких сгенерированных номеров пунктов.
10. **Валидация и публикация:** схема, времена, изображения, сохранение результата и очистка.

Текущий NanoDet/CV baseline допустим как отправная точка. Добавление VLM возможно только после проверки лицензии, локальности, улучшения качества и времени на целевом железе. Обучение большой модели с нуля не является обязательством.

### 8.1. Допуск категорий

Типы определяются после аннотации. Минимальные условия допуска: видимый признак, положительные примеры и сложные отрицательные, нормативная применимость, проверенные FP/FN.

Текущие EV01/EV02 — не подтверждённая таксономия всего датасета:

- **EV01:** приход клиента к уже пустому месту не доказывает уход кассира до окончания обслуживания. Для такой нормы нужен подтверждённый контекст обслуживания и ухода.
- **EV02:** статичный неизвестный предмет не равен наличным. Без достаточного распознавания предмета нельзя объявлять признак нарушения хранения денег только на основании фоновой разности.

Оговорка «возможно» не заменяет отсутствующий объективный признак. Неопределённость и причины отказа от гипотезы хранить внутренне.

Организатор допускает неизвестные классы на тесте. Реализовать разумный охват наблюдаемых паттернов, но не обещать обнаружение любых нарушений. Техническая невозможность анализа → failed; исправный анализ без достаточных оснований для события → два предусмотренных вердикта с осторожным объяснением ограничений в UI.

## 9. Нормативные правила

**[К]** Источники только в разрешённой юрисдикции РК. Базовые кандидаты:

- №231 от 29.11.2019: https://adilet.zan.kz/rus/docs/V1900019680
- №14 от 24.02.2020: https://adilet.zan.kz/rus/docs/V2000020075

**[У]** Конкретные пункты, редакции и применимость требуют отдельной проверки. Наличие записи `approved` в текущем JSON не заменяет подтверждения.

НПА №120 об операциях в самом Национальном Банке не применять к ForteBank автоматически.

Реестр [П]: `rule_id`, название/номер акта, официальный URL, пункт либо честная общая ссылка, проверенная редакция/дата, цитата, `event_type`, `observable_predicate`, `required_context`, `cannot_infer`, reviewer, `draft|approved|rejected`.

В выдачу допускается только `approved` и только при выполнении требуемого визуального контекста. FAQ допускает ссылку на акт без точного пункта, но не неверную трактовку. Нельзя объявить правило применимым лишь потому, что текст пункта существует.

Описание результата: наблюдаемый факт → почему требует проверки → источник → существенные ограничения. Юридическое или дисциплинарное заключение не выдаётся.

## 10. Безопасность, хранение и эксплуатация

- **[П]** HTTPS, секреты вне репозитория и образа, безопасные сессии, ограничение запросов.
- **[П]** Лимиты размера, длительности, разрешения/пикселей, CPU/RAM и времени; защита от вредоносных контейнеров и path traversal.
- **[П]** Видео и JPEG вне public webroot; доступ только через авторизованный backend.
- **[П]** TTL оригиналов, превью, evidence, JSON/БД и временных файлов согласован; автоматическая уборка проверяется также после ошибок.
- **[У]** Разрешённый срок хранения материалов уточняется по условиям хакатона. 72 часа в текущем compose не считать автоматически согласованным сроком.
- **[П]** До удаления результата по TTL гарантировать согласованное окно получения JPEG. После удаления — документированная недоступность, не пустой отрицательный результат.
- **[П]** Логи: job_id, стадия, latency, код ошибки, версия модели. Не логировать ключи, исходные видео, JPEG/base64 и описания тестовых сцен.
- **[П]** Healthcheck отражает не только HTTP, но готовность весов/worker; технические детали не раскрываются публично без необходимости.
- **[П]** Фиксировать версии зависимостей, hashes весов, источник и лицензию каждого компонента, конфиг и версию pipeline.
- **[П]** Docker Compose запускается по инструкции на чистом сервере. Нельзя зависеть от недокументированной внешней Docker-сети или отсутствующего env-файла; поставляется безопасный `.env.example`.
- **[П]** Offline-проверка выполняется с заблокированным внешним egress, не только с переменными окружения offline.

## 11. Оценка качества

Отчёт содержит:

- video-level TP/FP/FN/TN, precision, recall, F1;
- необработанные/failed видео отдельным числом, без скрытого исключения из качества;
- ошибки локализации на сопоставленных событиях и полноту локализации;
- точность типов по экспертной разметке;
- проверку релевантности JPEG;
- ошибки правовой привязки;
- отдельный результат другого ракурса либо отсутствие такого теста;
- mean/P95/max E2E latency на указанном железе, включая очередь и получение JSON.

Метрики на данных настройки не объявляются независимым holdout. Дубликаты не должны искусственно увеличивать число независимых примеров. При нескольких событиях использовать документированное сопоставление с reference events, а не только ближайший удобный таймкод.

Числовые обещания точности устанавливаются после baseline; исходный кейс не задаёт минимальный F1. Нулевые FP/FN на будущих видео не гарантируются.

## 13. Порядок реализации

1. Manifest, экспертная аннотация, группы дубликатов и split.
2. Исправление upload/queue lifecycle, безопасного результата, общего deadline и строгого публичного API.
3. Фиксация браузерного контракта и выдача fixtures Frontend.
4. Baseline на реальных видео, анализ пропусков/ложных срабатываний, утверждение классов и норм.
5. Уточнение времени/evidence, калибровка и интеграция UI.
6. Публичный deployment, offline/security/concurrency E2E, отчёт и rehearsal.

Работа над каркасом API и аннотацией может идти независимо. Нельзя объявлять ML готовым только по успешным тестам каркаса.

## 14. Definition of Done и поставка

Backend принят, когда:

1. BE-01–BE-19 проверены с фактическими доказательствами; непроверенные пункты обозначены явно.
2. Публичные UI/API доступны, ключ жюри передан отдельно безопасным способом.
3. Новый MOV обрабатывается без ручного вмешательства и внешних моделей.
4. Сквозной лимит 300 секунд подтверждён на целевом железе; параметры и ограничения нагрузки опубликованы.
5. Есть честный отчёт качества, утверждённые типы, нормативный реестр и перечень известных ошибок.
6. Поставка включает исходники, тесты, manifest/split/аннотации в разрешённых пределах, model/license manifest, конфиги, compose, `.env.example`, README и runbook очистки/восстановления.

Публичный адрес без работающего анализа, выдуманные нормы, облачный inference, фиктивные метрики и отрицательный вердикт вместо технической ошибки не являются допустимой сдачей.
